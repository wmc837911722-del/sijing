# 思径开源与企业获客策略

制定日期：2026-10-16。当前版本：0.3.0 开发预览。

目标是通过可验证的产品体验建立技术信任，再提供企业部署、技术支持与定制开发服务。当前仓库保持私有，仅所有者访问；产品完善并完成发布验收后，再由维护者主动公开。公开不由日期、提交次数或版本号自动触发。

## 产品与客户

优先服务接手陌生或遗留系统的研发负责人、技术支持和项目交付团队。核心场景是“业务规则在哪里、为什么出现这个结果、依据是什么”，并在需要时衔接只读数据查询和报表。

技术负责人通常关注接入难度、业务答案可靠性、数据外发边界与维护成本。展示一个能复现的业务问题，比堆砌模型平台数量更有说服力。暂不宣传尚未实现或验收的多用户权限、企业级服务承诺、完全离线推理和全仓库准确率。

## 分阶段开放

| 阶段 | GitHub 访问范围 | 主要工作 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 私有开发（当前） | 仅所有者，不邀请协作者 | 完善核心流程、积累失败样例、整理文档 | 核心闭环可重复验证，已知限制明确 |
| 定向试点（可选） | 源码仍私有；有实际需要时再明确授权访问 | 在获准环境测试一个有限业务域，人工核验答案，记录接入和维护投入 | 试点有可验收结果，演示材料获准公开 |
| 公开发布 | 维护者主动将仓库设为 Public，所有人可浏览 | 发布源码、已验收安装包、示例与文档 | 满足下方公开门槛；开放时同步更新 README 状态 |
| 公开迭代 | 保持公开核心项目 | 修复问题、积累业务案例、提供收费实施和维护 | 按实际使用与交付结果调整产品和服务 |

“完成”指本次承诺的核心流程与公开验收完成，不要求所有未来想法都实现。若采用公开预览，也须明确版本性质及未完成项，不能把开发快照标成稳定企业版。

GitHub 私有仓库控制从 GitHub 访问源码的范围，不提供定时开放或下载后回收副本的能力。公开时应复查整个可访问的提交历史及 Actions 记录；GitHub 明确说明，从私有转为公开会使 Actions 历史和日志对所有人可见。[官方可见性说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)

## 获客路径

1. **展示问题与证据。** 公开后制作一段使用合成或获准脱敏数据的演示：导入代码、形成业务笔记、沿链接回答一个具体问题、打开代码引用核验；数据问题再演示只读查询。展示一次真实限制与处理过程，不制作虚假的成功率。
2. **降低首次体验成本。** README 首屏说明适用人群、示例入口、已验收平台、运行步骤和数据边界。用户先体验示例，再选择自己的获准仓库与模型；开源自助使用不强制登记联系方式。
3. **围绕场景传播。** 发布接手遗留系统、业务规则追溯、技术支持排障、数据口径核对等案例文章。每篇连到一个可复现示例和项目主页。未经客户许可，不发布其名称、源码、数据、内部地址或使用结果。
4. **收集有限需求。** 在服务咨询 Issue 中只收集环境类型、待解决问题、预期交付与可公开的约束，不收集密钥、仓库凭证或业务明细。敏感材料在双方明确渠道、授权和保密安排后交换。
5. **开展付费试点。** 从一个仓库、一个业务域或一个数据主题开始，确认输入、交付物、人工验收问题集、时间范围、费用及不包含事项，避免先承诺覆盖全部系统。
6. **按需求持续服务。** 试点有实际价值后，再谈定制集成、知识维护和持续技术支持。项目咨询不自动转为营销订阅，也不默认安装遥测。

当前仓库仅本人可见，外部客户无法通过这里提交咨询；咨询入口为将来公开阶段准备。本次不公开发布推广页、不发送营销消息，也不创建公开 Release。

## 收费服务与开源边界

| 服务 | 典型交付 | 验收示例 |
| --- | --- | --- |
| 企业环境部署与接入 | 环境诊断、安装配置、内网 Git/代理/CA、获准模型和只读数据库连接说明 | 在指定设备可重复启动与连接，数据外发路径可解释 |
| 业务知识初始化与核验 | 限定业务域的 Markdown 笔记、来源引用、待确认清单、人工修订记录 | 双方约定问题集的答案可追溯；缺失证据被明确保留 |
| 定制开发与集成 | 经范围确认的连接器、MCP 接入、业务报表或流程改造 | 按约定接口与业务用例验收，明确通用代码和客户专属部分归属 |
| 持续技术支持 | 故障排查、升级协助、知识增量更新检查与质量回归 | 合同中约定响应范围、时间和交付记录，不在开源文档中虚构 SLA |

费用来自实施投入、专业判断、定制成果及服务责任。报价应区分试点实施、定制开发与维护；模型 API 和第三方资源费用需明确由谁承担。当前没有已验证的统一定价，不在页面上编造套餐价格或客户案例。

现有代码采用 MIT，保持 `LICENSE` 不变。MIT 允许获得副本的人在遵守许可条件的前提下商用、修改和再分发，因此不能把“商业使用权”包装成必须另外购买的服务，也不能仅靠私有可见性承诺接收副本的人不得转发。未来若要调整许可或设置客户专属代码边界，必须单独决定并核对权利归属，不能在 README 中附加与现有许可冲突的限制。

## 公开发布门槛

- 核心闭环通过：接入仓库、绑定获准模型、业务分析、引用核验、人工修订、Git 增量更新与冲突处理、业务问答；只读数据与报表按实际支持范围验收。
- 只对已完成实际安装及运行验证的平台提供对应支持承诺；Windows、macOS、Linux 分别记录，构建工作流存在不代表已验收。
- 对要推荐的模型做真实服务测试，记录具体模型、案例与局限。当前通用分析提示词仅完成同模型开发集测试，Kimi、DeepSeek、通义千问的跨厂商验证尚未完成；候选提示词也尚未替换产品。
- 检查准备公开的提交历史、代码、图片、配置、Issues、Actions 日志与产物，排除凭证、客户内容和未获授权材料；现有本地真实数据目录不上传。
- 明确第三方依赖和素材许可、已知问题、代码外发条件、模型费用及安装限制；有可复现的示例、上手文档、版本记录与反馈入口。
- 维护者核对交付范围与仓库设置后再切为公开。公开后不能通过重新设为私有收回别人已有的副本。

## 衡量是否带来客户

先建立实际基线，每月从自愿反馈和试点记录复盘；没有证据时不设虚假的增长保证。

| 指标 | 口径 | 用途 |
| --- | --- | --- |
| 首次有效任务完成率 | 开始自有仓库试用的团队中，完成一次带引用且经人工核实业务问答的团队占比 | 判断上手是否真正有效 |
| 持续使用率 | 首次成功团队中，在约定观察周期内再次完成真实业务任务的团队占比 | 判断产品是否有持续价值 |
| 付费试点转化率 | 有明确需求、授权范围和试点条件的有效咨询中，签订付费试点的比例 | 判断商业服务是否匹配需求 |

Stars、浏览量和下载量可作传播参考，不作为获客成功的替代指标。潜在客户资料、报价、合同和私有试点记录保存在独立的私有位置，不能放进未来会公开的仓库。

## 接下来的执行顺序

1. 完成此次私有上传，保留仅所有者访问；继续开发及测试。
2. 配置获准模型，在一个有限业务域完成可复现的分析与人工核验，补上真实模型测试。
3. 准备可公开演示、平台验收记录和服务范围，按门槛逐项核对。
4. 确定公开版本后调整可见性，发布经过验证的产物与场景文章；再从真实咨询选择付费试点。
