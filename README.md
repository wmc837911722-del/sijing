# 思径 · Sijing

**看懂业务，找到依据。**

![思径图标](build-resources/branding/sijing/icon-dark-128.png)

从代码建立可编辑的 Markdown 业务知识网络，用于业务技术支持、只读数据查询和报表，并通过 MCP 提供给其他 AI 工具。

项目原名 BusinessMap，自 0.2.8 起使用 **思径 · Sijing** 品牌。图标由 S 形路径与起点圆点组成，对应从问题出发、沿业务地图追溯依据。浅色和深色图标与桌面主题协调；品牌源文件见 [图标目录](build-resources/branding/sijing/)。

**当前为 0.3.0 开发预览版，仓库处于私有开发阶段，仅所有者访问。** 功能完善并完成公开验收后，再由维护者将仓库公开；当前没有公开下载渠道，也不承诺生产级服务。目标平台为 Windows、macOS 和 Linux。原生平台构建与实际运行验证分开记录：本地可验证 Windows，其余平台由仓库内的构建工作流提供打包流程，不能视为已经通过运行验证。

## 适合谁

思径面向需要接手陌生代码、解释业务规则和处理业务数据问题的研发与技术支持团队。例如，面对“订单取消后为什么不能立即退款”，团队可以从已有业务笔记沿双链查阅规则、核对代码来源，再判断是否需要查询只读数据。回答质量取决于代码覆盖和模型表现，关键规则应由业务人员核验。

先用自带示例体验，再接入公司允许使用的仓库与模型。需要企业环境接入、业务知识初始化、技术支持或定制集成时，可查看[企业服务范围](docs/SERVICES.md)。开源与商业服务的阶段安排见[开放计划](docs/OPEN-SOURCE-STRATEGY.md)。这些是拟提供的服务方向，具体交付范围和验收方式需另行约定。

**数据边界：**代码导入不执行仓库代码；主动进行 AI 分析时，会把必要代码片段发送给仓库绑定的模型服务。内网 Git 接入能力不等于模型推理全程不出内网；企业应使用获准的模型地址。Markdown 知识库保存在本机，数据库查询受只读连接及语句校验约束。

首版按 Windows x64、macOS Intel x64、macOS Apple Silicon arm64、Linux x64 四个目标构建和验收。0.3.0 增加由模型逐步选择工具的 Markdown 知识网络查阅，支持搜索、大纲、章节分页、双链与反链，保留 Kimi 等 12 个国内模型平台预设及调用兼容处理，保留思径品牌、桌面视觉与布局、企业私有 Git 接入与仓库模型绑定，以及各平台原生构建流程。各目标的安装包、环境和实际进度见 [三平台说明](docs/PLATFORMS.md)。

0.3.0 的 Windows x64 产物命名为 `release/Sijing-0.3.0-win-x64-setup.exe`（安装版）与 `release/Sijing-0.3.0-win-x64-portable.exe`（便携版）；实际交付、校验和和各版本测试结果见 [验收记录](docs/VERIFICATION.md) 与 `release/SHA256SUMS.txt`。既有交互与图谱专项见 [交互复验](docs/UX-REVIEW.md) 与 [图谱性能记录](docs/GRAPH-PERFORMANCE.md)。安装包不需要用户预装 Node.js 或 Python。

## 产品与功能

桌面主导航固定为 **模型配置 → 项目与仓库 → 数据库 → AI 问答 → 业务地图**。接入业务项目时分别填写前端仓库、后端仓库，统一生成项目业务知识、地图和总结，各仓仍独立同步与保存来源。模型配置集中管理不同平台的服务；数据库内包含查询与报表；业务地图内包含 Markdown 文档和关系图谱。AI 问答支持项目范围、单仓范围及历史会话。界面采用黑白灰配色，提供浅色、深色两套主题并记住用户选择。

0.2.7 的界面借鉴 Apple 的原生桌面设计：浅色采用银白层次，深色采用石墨层次，搭配系统字体、清晰的内容层级和统一的控件与间距。业务地图在窄窗口中自动收起右侧面板，仍可通过窗口顶部的面板按钮手动打开。

- 界面高亮引导：首次打开自动介绍 8 个使用步骤，可跳过、返回、暂停去操作；左下角随时继续或重看。参见 [上手教程](docs/GETTING-STARTED.md)。
- 本地 Markdown Vault：目录、标签、全文搜索、笔记页签、阅读与 CodeMirror 编辑、`[[双向链接]]`、反向链接、全局及局部关系图谱。
- 图谱探索：拖动节点带动关联节点、指针位置平滑缩放、邻居高亮、按倍率淡入标签；筛选、阅读笔记、主题和窗口调整保留视角。后台线程计算布局，支持 WebGL2 加速及 Canvas 回退；遵循系统减少动态效果设置。布局缓存仅保留当前窗口内的最近 12 个图谱视角。
- 人工编辑：保存采用内容版本检查，外部文件变化会刷新；冲突保留当前编辑内容，由用户处理。
- 内容分层：业务知识按项目名称与实体、流程、规则、数据口径归档到 `01-Wiki`，地图导航放在 `02-Areas/业务地图`，分析总结放在 `03-Projects`。普通文档只讲业务，代码、来源坐标、提交和分析回执保留在内部，不写入公开 Markdown 或图谱。
- 业务问答：选定项目或范围后，只从已发布且授权有效的业务知识查找规则与流程。普通问答不提供源码检索、源码读取或源码弹窗；历史回答、参考来源与本地摘录同样受此边界限制。代码分析在内部逐批覆盖纳入范围的源码，来源核验与业务语义正确性分别验收。
- 分析失败会保留受控状态和说明；问答接近预算时预留一次仅整理答案的请求。若已读证据无法完整容纳，只能说明已确认部分与缺口。
- 代码仓库：支持本地 Git 目录、HTTPS 账号和 Token/密码、SSH Agent 或已有密钥；适用于可连接的公网及公司内网 Git 服务。提供连接测试、分支选择、代理和公司 CA 配置、凭据更新和同步重试。**导入阶段不调用模型，也不执行仓库代码。** 同步失败保留已有地图。
- AI 业务分析：以业务项目完整分析前端和后端，清点全部受支持源码，按完整行分批处理并保存断点，完成后按实际业务主题生成知识卡片、地图和总结。界面区分文件、批次、模块进度及排除项；旧取样结果明确标为局部预览。每个参与仓库必须明确绑定同一获准模型目标；默认模型切换不影响绑定。成员代码更新后旧结果标为过期。未分组仓库保留原单仓分析与自动更新能力。人工修改产生独立候选，不静默覆盖。详见[完整分析约定](docs/FULL-ANALYSIS.md)与[业务项目约定](docs/BUSINESS-PROJECTS.md)。
- 模型接入：Kimi、DeepSeek、通义千问、智谱、豆包、硅基流动、腾讯混元、百度千帆、MiniMax、讯飞星火、阶跃星辰、百川，以及 OpenAI、Anthropic、Gemini、Ollama 和自定义兼容服务。预设提供地址与填写说明，模型 ID 不设白名单；支持非流式文本调用；渐进问答要求所选模型支持工具调用，模型预设和连通测试不等于已验证该能力，账号开通范围以服务商为准。[平台与凭据说明](docs/MODEL-PROVIDERS.md)。凭据使用系统凭据库，系统不支持时仅本次会话保留。
- 本机 Codex：可通过已安装的官方 Codex CLI 和 ChatGPT 登录执行代码分析、业务归纳，消耗该账号的 Codex 额度，无需填写 API 密钥。该模式关闭工具执行，暂不支持渐进工具问答；运行仍需联网。项目更换模型时可显式选择核验并接续已有结果，保留原模型来源与回执，继续未完成批次；绑定与迁移本身不发送代码。CLI 不提供服务端输出 token 硬上限，应用通过提示、结构化输出、实际用量和本地大小限制验收返回结果。
- 技术支持：AI 自主选择搜索、目录、大纲、章节读取及双向关联工具，根据每轮查阅结果决定下一步，并以实际读取过的笔记作为引用。长文可分页读取，不要求从根目录开始，也不固定为一次 top-k 摘录。界面显示可展开的实际探索步骤，可停止后续操作；笔记、代码版本或授权变化后中止旧上下文。会话保存在本机并按知识库隔离；每次可选择模型及仓库，不改变默认模型。未配置模型时提供明确标记的本地知识摘录，不模拟 AI 推理。
- 数据查询：SQLite、PostgreSQL、MySQL 适配；直接 SQL 和 AI 数据问答共用语句校验、表范围、只读连接、超时与结果上限。
- 报表：固定引用一次真实查询的结果与执行时间，支持表格、柱状图、折线图。
- MCP：9 个只读工具，提供知识目录、搜索、大纲、章节与分页读取、双链/反链、关系图、数据结构及查询；知识导航实现与内置 AI 共用，可独立于桌面窗口运行。
- 缓存观测：常规探索保持固定系统提示与工具定义并追加工具结果；预算收尾使用独立的有界上下文，只允许整理答案或说明缺口。Anthropic 使用缓存检查点。汇总实际输入、输出和缓存 token，缺失值保持未知，不承诺固定命中率。查询结果直接呈现给用户，不回传模型，也不会作为实时回答缓存复用。

首次启动会创建**明确标记的示例知识库和示例 SQLite 数据库**。它们用于体验界面，不代表已分析用户的仓库。

## 本地开发

需要 Node.js 24、Python 3.12、Git；SSH 功能和完整后端测试还需要 OpenSSH 客户端。应用安装包自带 Python 服务；使用代码仓库功能仍需系统可执行 Git。

```bash
npm ci
node scripts/setup.mjs
npm run dev
```

生成生产界面并以桌面形式运行：

```bash
npm run build
npm start
```

开发数据默认位于项目 `.local-data/`。可通过 `BUSINESSMAP_DATA_DIR` 指定独立目录。

在这台 Windows 开发环境，项目、依赖、构建、临时文件及测试结果均放在 `D:\BusinessMap`。为避免工具默认缓存到系统盘，可在 PowerShell 使用：

```powershell
$env:TEMP = 'D:\BusinessMap\.tmp'
$env:TMP = $env:TEMP
$env:npm_config_cache = 'D:\BusinessMap\.cache\npm'
$env:electron_config_cache = 'D:\BusinessMap\.cache\electron'
$env:ELECTRON_CACHE = $env:electron_config_cache
$env:ELECTRON_BUILDER_CACHE = 'D:\BusinessMap\.cache\electron-builder'
$env:PIP_CACHE_DIR = 'D:\BusinessMap\.cache\pip'
```

安装版在 Windows 有 D 盘时默认使用 `D:\BusinessMapData`；其他环境使用对应操作系统的应用数据目录。Markdown Vault 可在界面中切换。系统凭据库的位置由操作系统管理。

改名保留原有应用身份、数据目录及系统凭据库标识，已有知识库、模型配置、仓库连接和凭据继续使用原位置，无需因改名迁移。项目目录 `D:\BusinessMap`、`BUSINESSMAP_*` 环境变量和 MCP 工具名也保留兼容；MCP 服务显示名称为 `Sijing`。应用程序名称为 Windows 的 `Sijing.exe`、macOS 的 `Sijing.app` 和 Linux 的 `sijing`。

## 试用流程

1. 打开示例知识库，点击双链、反链和图谱节点，编辑一篇 Markdown 并保存。
2. 在“数据库”选择示例数据库，执行默认聚合查询，保存并查看报表。
3. 在“模型配置”添加自己的模型服务与模型 ID，点击测试检查实际连通性。
4. 在“业务地图”切换到自己的知识库，再到“项目与仓库”点击“接入业务项目”。填写项目名称、同一业务的前端仓库地址和后端仓库地址，点击“接入项目与前后端仓库”。
5. 等两个仓库都显示“已就绪”，在项目卡片点击“绑定项目模型”，选择允许接收这两个仓库代码的模型并确认。点击“完整分析项目”后，必要代码片段会发送给该模型。
6. 文档保存后，回到“业务地图”。从知识目录的“业务地图”打开项目地图，沿链接阅读业务主题，在“项目总结”打开分析总结。
7. 在“AI 问答”新建会话，选择知识模式解释业务，或选择数据模式与数据源，按实际需要生成并直接执行只读 SQL。
8. 后续提交前端或后端改动后，在对应仓库点击“同步变更”。项目提示代码版本变化时，点击“重新完整分析”更新业务文档。
9. 在“模型配置”复制 MCP 配置，粘贴到支持 MCP 的工具中。使用当前配置展示的完整命令，避免依赖工作目录。

## 构建与验证

```bash
npm run test:backend
npm run build
npm run test:desktop
npm run package
npm run test:packaged
npm run test:packaged:all
```

`package` 使用 PyInstaller 打包当前平台 Python 服务，再由 electron-builder 生成本平台安装包。产物位于 `release/`。`package:dir` 生成未封装目录，适合验证。

GitHub 私有开发阶段的四平台打包仅支持手动触发，避免每次推送自动消耗构建额度；仓库公开后恢复工作流中既有的推送与 PR 自动构建。上传代码不等于已通过云端构建或平台验收，安装包需另行验证后发布。

`test:packaged` 检查主流程和 MCP；`test:packaged:all` 还会检查当前系统的窗口、快捷键、企业仓库认证与模型绑定、引导和工作区交互，是四个原生构建任务的完整验收入口。

- Windows：NSIS 安装程序及便携版本。
- macOS：DMG 与 ZIP。
- Linux：AppImage 与 DEB。

`.github/workflows/build.yml` 配置了四个原生系统/架构任务，依次执行后端测试、桌面平台分支测试、打包、桌面与 MCP 验证及完整交互专项，上传安装包及验证附件。Linux 使用 Xvfb 提供测试显示环境。该工作流尚未在远程仓库运行，不能视为三平台已经验收。项目初始版本没有配置代码签名或 Apple 公证；正式分发需要维护者配置证书并完成对应平台验证。

测试及截图写入 `artifacts/`，测试数据写入 `.tmp/`。真实模型平台、PostgreSQL 和 MySQL 的实际环境验收，需要使用专门的测试凭据进行；HTTP 适配器的受控响应测试不代表已连接真实服务。

## 数据与执行边界

桌面渲染器处于沙箱中，只通过受限 IPC 调用主进程。Python 服务仅监听回环地址，每次启动使用随机令牌。笔记中的 HTML 或脚本不作为可执行应用代码。服务不执行导入仓库中的程序。

企业 Git 访问使用本机网络，内网/VPN 需事先连接。HTTPS 保持证书验证，SSH 保持主机指纹验证；有口令的私钥先加入系统 Agent。凭据保存在系统凭据库或当前会话，接口和模型上下文不包含密码。网页登录、交互式 SSH 认证、自定义 SSH 命令和跳板机暂不支持；这些环境可先用公司的 Git 客户端克隆，再接入本地目录。本地目录观察已提交 HEAD，不代替客户端拉取远端。远程明文 HTTP 仅允许本机测试。

仓库绑定适用于应用内部分析和问答：全库检索过滤当前模型无权接收的仓库笔记，会话历史按模型目标和授权范围隔离。它不是全局数据防泄漏系统；外部 MCP 客户端的模型、手工复制且移除归属的内容、用户输入及数据库数据需独立管理。升级前已接入的仓库保留原地图，下一次 AI 分析前需先绑定模型。

数据库执行由独立的确定性工具层负责。SQLite 以只读 URI 连接并启用 authorizer；PostgreSQL/MySQL 使用只读事务并检查账号权限。未知函数、写入、多语句、越权表、锁定操作等被拒绝。默认 5 秒查询限制、最多 1,000 行及 2 MB 结果。允许表范围可在数据源配置中收窄。

本地查询结果与报表包含所查数据，会保存在应用数据目录。数据库密码和 API 密钥不写入 Markdown、配置数据库或日志。单机预览版不提供多租户隔离、企业授权与自动数据保留策略。

会话保留最近 200 条消息（界面会提示历史截断），模型使用最近 8 条同作用域的历史。切换仓库、模式或数据库后不会把旧作用域的回答继续拼入模型上下文。正在生成的同一会话拒绝并发请求；失败和中断状态会保留。“新建对话”返回同一个未发送草稿，首次发送时才建立历史会话。单次输入上限为 8,000 个字符，超限会保留输入并提示缩短。输入草稿在本次窗口的导航和会话切换间保留，未发送草稿不会在退出后恢复。

SQL 编辑草稿和最近一次结果按数据源分别保留，切换页面、数据源或往返报表不会清空；这些工作区状态不会在退出应用后自动恢复。修改 SQL 后，界面明确标记结果仍来自上次执行。保存报表引用打开保存表单时选定的结果快照。

## 预览版边界

- 尚未承诺完整 Obsidian 插件、Canvas、块引用或全部 Markdown 扩展兼容。
- 业务分析有源文件、上下文及输出限制，不代表已穷尽任意大型仓库。结论仍应核对引用依据。
- Git 自动更新在桌面后台服务运行期间生效；退出应用后不会继续托管后台分析。MCP 进程可独立检索和查询。
- 跨服务调用链、部署版本与数据库 schema 精确绑定、多文件业务版本原子发布仍需进一步增强。
- 真实模型返回的业务规则和 SQL 语义准确性，需要在目标业务上建立评估集；只读执行保护不等于指标口径正确。
- 尚未为报告增加 PDF/Excel 导出，也未实现多用户实时协同。

```text

src/                 React 知识工作台、编辑器、图谱和工具界面
```
